## 1. 接口一览

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/reco/weekly-hot` | 公开 | 每周热门榜单 |
| GET | `/api/v1/reco/personal` | 可选登录 | 个人推荐（未登录回退热门榜） |
| POST | `/api/v1/reco/seats` | 公开 | 座位推荐（已有，不属于本次） |

两个新接口都在 `RecoController`，权限注解 `@Public`。`SecurityConfig` 已放行 `/api/v1/reco/**`，无需额外配置。


## 2. 数据模型（3 张表）

| 表 | 用途 | 关键字段 |
|---|---|---|
| `reco_stats` | 每片一行的**周信号物化表** | `week_orders` 近7天订单数、`week_clicks` 近7天点击数、`rating_norm` 评分归一(0–1)、`freshness` 新鲜度(0–1)、`hot_score` 物化热门分、`computed_at` |
| `reco_weight` | 每城一行的**热门公式权重** | `w_orders/w_clicks/w_rating/w_fresh`，默认 0.45/0.25/0.15/0.15 |
| `reco_clicks` | 影片点击**日计数表** | PK `(movie_id, click_date)`，`cnt` 当日点击数 |

> `reco_stats` 存的是**原始计数 + 评分/新鲜度**（week_orders/week_clicks 是 INT 原始值），`hot_score` 只是按默认权重算的缓存；GET 时按请求城市的权重**重新算**，保证城市权重即时生效。

## 3. 算法原理

### 3.1 每周热门

```
hotScore = 100 × ( w_orders × normOrders
                 + w_clicks × normClicks
                 + w_rating × ratingNorm
                 + w_fresh  × freshness )     // clamp 到 [0, 100]
```

- **week_orders**：近 7 天 `order_ticket(status='issued')` JOIN `show_schedule` 按影片计数（订单表没有 movie_id，靠 JOIN 补）。
- **week_clicks**：近 7 天 `reco_clicks` 按片 SUM。
- **ratingNorm** = 评分 / 10（8.8 → 0.88）。
- **freshness**（由上映日计算）：
  - 已上映 `hot_showing`：`1 - 距上映天数/90`，90 天内线性衰减，超 90 天为 0；
  - 待映 `coming_soon`：`1 - 距上映天数/30`，临近上映新鲜度高；
  - `off`：0。
- **归一化**：week_orders / week_clicks 在当周全片上做 `值 / 最大值`（min-max 且最小为 0）。这一步**关键**——订单原始计数可能是几十，而评分/新鲜度只有 0–1，不归一化订单量会把其它维度压死。
- **heatTag**：rank 1=本周爆款，2–3=人气佳作，4+=正在热映。

### 3.2 个人推荐

```
personalScore = 0.5 × genreMatch + 0.2 × tagMatch + 0.2 × ratingNorm + 0.1 × hotScore
```

- **画像**：
  - 显式偏好 = `user_profile.prefer_genres_json`；
  - 行为偏好 = 想看的电影类型 ∪ 已购（issued 订单）的电影类型。
- **genreMatch** = Jaccard(候选片 genres, 显式偏好)  ——「用户明确说喜欢什么」
- **tagMatch** = Jaccard(候选片 genres, 行为偏好)  ——「用户实际看过/想看过什么」
- **ratingNorm** = 评分/10；**hotScore** = 物化热门分/100。
- **同类型连续 ≤3**：按分数降序贪心排布——主类型（genres[0]）与上一片相同且已连续 3 片时，该片**顺延到末尾**再补，避免首页连续刷同一类型。
- **reason 文案**：`genreMatch ≥ 0.5`→「符合你偏好的{类型}」；否则 `ratingNorm ≥ 0.85`→「口碑佳作」；否则 `hotScore ≥ 0.7`→「本周热门」；否则 null。
- **未登录**：`mode=fallback_hot`，直接复用热门榜，`personalScore=hotScore/100`，reason=「本周热门」。

## 4. 核心流程（两种触发方式）

```
调度器 RecoStatsScheduler（每 10 分钟）        GET /reco/weekly-hot 或 /personal
        │                                            │
        └──────────────► recomputeStats() ◄──────────┘
        （reco_stats 为空或 computed_at 超 1 小时时 GET 同步重算兜底）
                │
                ├─ 近7天订单计数（JOIN）   ─┐
                ├─ 近7天点击 SUM          ├─► 组装 RecoStats 列表
                ├─ ratingNorm / freshness ┘
                └─ 按默认权重算 hot_score，DELETE + 批量 INSERT 全量重写（事务内）
```

**点击埋点链路**：用户访问 `GET /movies/{id}` → `MovieServiceImpl.get()` 里 `recoClickMapper.incrClick(movieId, 今天)` → `reco_clicks` 当日 cnt+1（跨天自动新行）→ 下次重算进入 week_clicks。

**读代码的顺序建议**：`RecoServiceImpl` 从三个 public 方法读起——
`weeklyHot()` → `recomputeStats()`（数据从哪来）→ `personal()`（个性化怎么算），再回头看私有方法（`fillHotScore` 打分、`jaccard` 相似度、`enforceConsecutiveGenreLimit` 连续约束、`reason` 文案）。

## 6. 关键设计决策与取舍

| 决策 | 做法 | 为什么 |
|---|---|---|
| week_clicks 数据来源 | 新增 `reco_clicks` 日计数表，挂在影片详情接口 | 没有点击埋点基础设施；表小（movie×天），比 Redis 计数更持久可测 |
| 城市权重 | GET 时用 `reco_weight` 按城市**重算**排序，不直接用物化 hot_score | 城市权重即时生效，不用等重算 |
| 首次/过期兜底 | 榜单为空或 `computed_at` 超 1h → GET 同步重算 | 新环境没等调度器也能出榜 |
| 物化写库 | DELETE + 批量 INSERT 全量重写，用 `TransactionTemplate` | 全量重算保证一致性；事务避免「删了没写成」半空榜 |
| 同类型连续 | 贪心顺延（超限丢到末尾）而非均匀打散 | 实现简单、确定性可测 |
| §10.11 权重配置 | **未实现** | 前端无管理页，权重走默认算法 |
| 未登录个性化 | 回退热门榜 | 无画像可打分，回退最稳 |

## 8. 可能的演进（本次未做）

- `week_clicks` 换成真实埋点系统（PV/UV）而非详情访问计数。
- 排序靠 reco_weight 城市权重 → 后续可做运营可配（§10.11）。
- 行为偏好扩展：加入「收藏」「分享」等信号，或基于协同过滤（用户相似度）。
- 榜单缓存到 Redis，减少每次 GET 的排序计算。
